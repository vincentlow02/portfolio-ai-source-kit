# Portfolio AI: integration instructions for a coding agent

This item provides source and examples; it does not automatically integrate into an existing application. Read `.portfolio-ai/security.md` before deployment. Do not use Figma or call a paid model to perform setup.

1. Inspect the host's Next.js App Router, package scripts, paths, layout and existing security controls. Do not overwrite existing code or configuration. Check the installed files and dependency versions for conflicts. Preserve the host's design and functionality.
2. Inspect only material the owner has authorized you to inspect. Propose specific anonymously accessible same-origin URLs and their corresponding content files as potential sources, and separately identify protected paths. Ask the owner to approve the exact list before adding any content to the manifest, publishing a corpus, or accessing private material. Approval of public sources does not authorize private sources. Never add private material to the corpus. If approval is pending, do not run the corpus publisher; continue independent setup.
3. Use `.portfolio-ai/templates/portfolio-knowledge.config.ts` as a structural example to write a host-specific manifest. Use rendered sources for dynamic pages, static MDX only where supported, and protect private paths and descendants. Do not leave fictional Atlas records or names in the host. Configure `portfolio-assistant.server.ts` with the host owner's name, aliases, languages, project identifiers, and protected paths.
4. Adapt the provided example API route files to the host's app directory, resolving relative imports correctly. Integrate the existing `PortfolioChatPanel` into the host's layout without replacing it; configure the endpoint, published paths, languages and suggestions. Preserve selection, citation, history, follow-up, cancel, reset and mobile behavior.
5. Merge the example `next.config.ts` file-tracing entries and security headers with the host configuration. Add a build command using `tsx scripts/portfolio-knowledge/publish.mts`, preserving existing build requirements. Do not commit `.env.local` or disclose credentials. The owner supplies a dedicated Supabase project and model credentials using the template; review the SQL migration before applying it. Public access is disabled by default. Do not enable public access or deploy until the owner has reviewed the setup.
6. After source approval, build the corpus, run build and type checks, then exercise chat, source links, highlight-to-ask, follow-ups, cancellation, protected paths, authorization and quota failure. Use mocks for testing unless the owner separately authorizes paid calls. Check cited passages manually: structural citation validation cannot prove semantic correctness. Report what passed and any compatibility or privacy issues.

Template paths are examples, not files to copy blindly. The scripts assume the source kit lives at the application root; if the host uses `src/`, adapt imports and app routes consistently. Review the host's dependency manager and do not replace its lockfile.
